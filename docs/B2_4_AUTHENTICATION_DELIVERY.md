# B.2.4 — Authentication lifecycle delivery (review candidate)

Scope: definitive authentication state transitions inside the V2 authority and independent Kotlin protocol implementation. Enrollment state machine, policy-sync handshake, hardware TLS/biometric adapters and production cutover are not included. No finding is closed. No portable core extraction. V1 runtime remains unchanged until the coordinated cutover. This is a development component, not a partial production remediation.

## Host

`Authority::start_auth` consumes the existing atomic admission reservation and constructs the exact signed AuthCore from the owned request, stored host ID, verified peer HELLO nonces, exporter, identity, scope, trusted adapter context, policy revision and deadlines. It generates a separate uniform six-digit value using OS randomness/rejection sampling. Only the local adapter receives that value; it must display it to the original verified local interaction before transmitting the signed challenge. The adapter must use the actual TLS host signing key and not construct facts from remote assertions. The old dispatch/recheck primitives still cannot authorize authentication by themselves.

`auth_number` charges ingress, consumes the number stage, compares the single entry in constant time, rechecks authorization, signs the exact match and stores the exact expected response core. Wrong, duplicate or out-of-order input closes the bound channel. `auth_cancel` validates the request/session of the current channel before terminating it. `auth_response` consumes the request before checking the evidence, rejects a mismatching core, verifies the current enrolled biometric public key (not transport key), and checks principal generations, policy revision, grant, assurance, and expiry within the same transaction as the audit record. The trusted clock adapter is sampled again before commit and after commit; an expired operation cannot return local success. `auth-success` records accepted evidence committed by the authority, not proof that the IPC requester ultimately received the result. Success must be routed synchronously to the original owner/interaction and never used as a bearer token. Adapter must close the denied/terminal socket after optional informational result transmission. Local cancellation, disconnect and policy changes invalidate the owning live request.

`Peer` now carries both HELLO nonces. They must originate in the actual authenticated HELLO exchange. `auth-success` extends the strict audit event schema. Since no production V2 database has been deployed and migration is not required, recreate any disposable B.2.2/B.2.3 development database; never automatically reset an existing security database. Exact schema checking rejects a stale schema.

## Android-side protocol

`V2Authentication` validates signed AuthCore against the actual channel, host pin, stored credential, both nonces, exact policy intersection and freshness. It exposes manual number entry only after validation, then verifies the signed match before providing the exact ResponseCore transcript to the native biometric adapter. A signature must verify against the enrolled biometric key before a response can be constructed. Each transition is single-use and checks wall/monotonic clocks; failure is terminal. Policy is rechecked at each pre-response transition. Device adapter must invalidate on policy change/disconnect, serialize live UI/transport events, and use fresh per-use strong biometric CryptoObject signing for the returned bytes. JVM tests use software keys only. No evidence of Android Keystore or UI assurance is claimed.
