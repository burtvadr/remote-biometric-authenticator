# RBA V2 — System architecture

**B.1 design baseline · 2026-11-24 · proposed for acceptance, not implemented**

Source baseline: uploaded archive `2b8e76dea7dc544ba834d6f026b7177820e938d6`, with the delivered B.0 patch applied locally. No remote Git history or subsequent local changes were inspected. This document and the [V2 wire specification](../protocol/specification/PROTOCOL.md) govern new development; current V1 code and older descriptions are historical implementation evidence. No V2 production claim is made by merging these documents.

## 1. Objectives and non-goals

RBA authenticates a named OS principal for a specific operation by obtaining a fresh, hardware-backed, biometric-gated signature from a paired phone. It is not a general authorization engine, a remote shell, a fingerprint sensor emulator, or an OS access-control bypass. The OS retains the final access decision. The feature contract is [roadmap.md](roadmap.md). Breaking changes and fresh enrollment are intentional. No compatibility reader, optional legacy authentication, unverified hardware fallback, or temporary production authentication path is permitted.

## 2. Source-to-target map

| Existing source | Target responsibility |
|---|---|
| `linux/protocol` and `android/protocol` | One portable Rust wire codec, transcript and state-machine implementation; Kotlin is an adapter, not a second security implementation. |
| `crates/rba-enrollment`, `crates/rba-enrollment-jni` | Retain reviewed RFC 9382 library primitive, replace application context and lifecycle; consolidate JNI boundary. |
| `linux/rbad/src/{engine,authz,admission}.rs` | Portable core owns request transitions, grants, reservations, revocation and evidence checks. |
| `linux/rbad/src/{registry,config,audit}.rs` | Linux storage/configuration/audit adapters; atomic transactions through one core boundary. |
| `linux/rbad/src/{tls,transport,server,ipc}.rs` | Authenticated TLS streams, bounded listener, peer-authenticated local IPC. |
| `linux/{rba,pam-rba,polkit-agent,rba-sim}` | Thin local clients and test peer; simulator cannot enroll into production. |
| Android `DeviceAuthKey`, `BiometricGatekeeper`, `AuthenticatorRuntime`, `AuthPromptActivity` | Android-specific Keystore, trusted presentation, biometric and lifecycle adapters. |

New portable crate names proposed: `rba-protocol`, `rba-core`, `rba-android-jni`; keep `rba-enrollment` as a small independently tested primitive. Naming may be adjusted at review; no parallel runtime stacks. Shared core contains no OS accounts, Android APIs, sockets or filesystem paths. Platform adapters inject authenticated peer facts, CSPRNG, clocks, transaction store and signing operations. A typed state machine is the only authority for effect requests. JNI handles are opaque, bounded, generational and ownership-checked; never unvalidated pointers. Cancellation invalidates handles and discards secrets. Kotlin cannot manufacture an approval by supplying an arbitrary payload to a signing callback.

## 3. Trust boundaries

```
OS service / CLI -> verified local IPC -> daemon + portable host core
                                           | atomic durable store
                                           | scoped policy / admission
                                           v
                                mutually authenticated TLS 1.3
                                           |
                              portable device protocol via JNI
                                           |
                             Android UI + Keystore + BiometricPrompt
```

The production TLS peer authenticates a **transport** credential, never a biometric approval. Separate host identity, Android transport and biometric signing keys are enrolled as one binding. Device transport key is usable unattended, hardware-backed and attested; biometric key is hardware-backed and requires fresh strong biometric per signing use. Separate keys prevent unattended reconnection from consuming or impersonating approval. Host identity and TLS server key may be one P-256 key with explicitly reviewed TLS/key-usage constraints; V2 chooses one host TLS/identity key (certificate SPKI must match). Trust pins are exact public keys, not names or advertised hashes. Use TLS 1.3 with no resumption or early data, and exporter channel binding. Use the same TLS engine and profile over TCP and any future ordered BLE/ADB byte stream. No alternative unencrypted BLE auth. A BLE adapter that cannot implement bounded reliable ordered duplex streams remains unavailable. VPN/Tailscale changes routing, not trust.

Enrollment is a deliberately opened, bounded separate listener; no permanent permissive TLS verifier. It uses provisional self-signed TLS certificates plus proof of private-key possession, and mandatory SPAKE2 binding of actual handshake keys/channel and newly generated attested long-term device keys, then host verification of fresh key attestation and device/host explicit consent. Provisional TLS traffic is not trusted until PAKE confirms; only enrollment messages are permitted. No credentials or privileged operations before enrollment commits. Production and test trust roots, signing identities, data directories and sockets are disjoint.

## 4. Principals, callers and grants

Principal = opaque random 128-bit host-assigned ID; Linux adapter maps it to an explicitly enrolled account record `(uid, canonical NSS name, generation)`. Do not equate a username or reused UID with enduring identity. Support managed local accounts first: lifecycle changes (delete, rename, reuse, source changes) require explicit root-controlled deactivation/rebinding before an account becomes eligible, using account-management integration or an administrative barrier. NSS does not provide a universal immutable generation. Unmanaged identities, remote NSS without lifecycle evidence, ambiguous mappings and unobserved account lifecycle cannot claim stable identity and are not supported by V2 integration. Root/admin bypass of that lifecycle is outside the model; document and test this prerequisite before deployment. Account display names are not authorization IDs.

Kernel peer credentials plus a root-configured trusted adapter/channel establish caller identity. An ordinary caller can authenticate only their own principal using the CLI scope; it cannot claim a PAM or polkit scope by string. A trusted service adapter uses OS-supplied facts and explicitly configured service/action bindings, not untrusted client text, process names or guessed `/proc` attributes. If a platform cannot establish the requested operation or present intent reliably, disable that integration; do not fabricate it. In particular PAM `PAM_SERVICE` alone does not certify a command, action or remote origin. For sudo, a PAM-only adapter may attest the service authentication event, not exact command approval; elevated command-specific grants require a trustworthy operation adapter. OS recovery remains available.

Grant key = `(credential_id, approver_principal, target_principal, scope)` with exact typed operation and service. No wildcards, implied root grant, or implicit inheritance. Delegation is explicit, independently approved and audited; both identities shown. Host, device and account policies intersect: capabilities never create grants. Admin changes that expand grants require authorized local change and authenticated device consent for the exact revision; removals are immediate without consent. New enrollment grants only explicitly selected CLI self-authentication; no automatic elevated privilege. Recheck key, assurance, account mapping, policy revision, caller session and grant under the same serialized state boundary immediately before returning a one-time success to the original local request. A revoke/change ordered before that point prevents success; an already delivered result cannot be retroactively recalled. Never cache approvals for unrelated OS actions.

## 5. Admission, intent and request lifecycle

Distinct budgets for pre-auth connections/bytes, local authenticated callers, enrolled request ingress, pairing attempts and dispatched/possibly dispatched biometric prompts. Admission never depends on an attacker-supplied identity. An unauthenticated peer cannot burn another principal's prompt budget. Resource budgets protect parsing and queues; prompt budgets protect people. A global bound complements per-source limits; source addresses are not authentication. No unlimited key maps or unbounded queues.

Initial fixed policy (engineering defaults, not measured ergonomic guarantees; see wire spec for connection/byte caps): per verified local caller 30 requests/60 s; per enrolled connection 30/60 s over TCP or 15/120 s over BLE; global prompt 6/60 s, per target and per credential 3/60 s, elevated subset 1/60 s per target and per credential; pairing 5/300 s globally and per eligible local initiator. These are rolling windows; reservations commit atomically before dispatch. No increase merely to match transport capacity. At most one live request per target and per credential across transports. Charge potential prompts even on failure or lost packets; do not charge unrelated prompt counters for rejected requests. Ingress attempts are independently charged before expensive processing. Limits are centralized, versioned, bounded and testable. No dynamically weakening defaults or silently clearing budgets on restart. Persistent store failure denies new dispatch and success; backward wall-clock movement denies new reservations until a safe clock is established. Live deadlines use monotonic elapsed time.

A request originates from explicit local action, with a verified interaction channel capable of displaying a fresh six-digit number. Phone shows enrolled host, approver, target, exact operation and context provenance, requests manual number entry, and obtains fresh strong biometric only after host confirms that number. Number is never sent in the initial phone challenge, nor in logs, argv, clipboard or notifications. One guess per request; wrong input terminates it. No automatic prompt on unverified unsolicited network traffic. One request per TLS connection/session binding; multiple connections may carry unrelated requests. Failover requires a new challenge, number and budget reservation after terminally cancelling the old request. No transfer of an existing approval across channels.

State: `Created -> Authorized -> Reserved -> ChallengeSent -> NumberMatched -> AwaitingBiometric -> EvidenceVerified -> CommittedSuccess`; any error, denial, cancellation, policy change, timeout or disconnect leads to `TerminalFailure`. The core validates exact transition, immutable context and deadlines; consumes evidence once even on invalid proof; no background success after local requester exits. A request ID is unpredictable and never reused; restart drops all in-flight exchanges. Device cancellation cannot cancel a different connection/request. Local result is delivered only to its owning IPC request, not a transferable bearer token.

## 6. Durable state and recovery

Choose a **single SQLite transactional store** on the host, not separate writable per-device files. This intentionally supersedes the earlier per-device-file proposal: a pairing can revoke old credentials, add new grants and advance counters together, and crash consistency across files would otherwise require another transaction journal. SQLite is a mature transaction mechanism; use one writer, strict schema, foreign keys, uniqueness constraints, durable transactions and integrity checks. Journal mode DELETE with synchronous EXTRA on supported local storage, validate crash semantics in tests. No network filesystem support. A root-only `/var/lib/rba/v2/` holds database, host key/cert and lock; `/etc/rba/` holds administrator policy and trust anchors; `/run/rba/` holds protected sockets; `/var/log/rba/` holds redacted event logs. Root-only directories 0700 (socket parent may have carefully scoped traversal ACL); private files 0600. Never follow attacker-controlled symlinks. Fail closed on unreadable, corrupt, mismatched or unsupported state; never auto-reset. An explicit offline fresh-state initialization and re-enrollment is the sole cutover. Keep the old installation offline only for operator recovery; do not run V1 as a V2 fallback. Password and original vendor PAM routes remain independent. No runtime JSON for RBA-owned storage/IPC/logs; standardized external attestation revocation JSON is an external input, and JSON test fixtures remain permitted. Provide read-only `rba inspect` for human-readable inspection instead of treating raw file readability as a security requirement.

Enrollment persistence: phone first durably stages the new binding; host atomically commits new credential, explicit grants and revocations after verified proof and staging acknowledgement. Phone activates only after authenticated commit receipt. Lost receipt is resolved by authenticated read-only status using the exact transaction and enrolled transport key; no alternate enrollment or duplicate grant. No claim of distributed atomic commit: host may have committed while phone is still pending. Pending phone never signs; unresolved transaction may be explicitly revoked and re-enrolled. Before host commit, disconnect/cancel aborts only its own transaction; after commit, revocation is an explicit policy operation. Offline device unpair deletes active binding immediately and retains only a bounded revocation-only tombstone; no authentication from tombstone. Retry revocation over enrolled mTLS or inside a new PAKE-confirmed enrollment for the same host. Expired tombstones require host-side removal. Store token hashes on host, never log tokens.

## 7. Attestation and Android release

Use fresh host challenge bound to the enrollment session and both transport identities; generate new keys rather than retrospectively claiming assurance for existing keys. Verify certificate path to administrator-configured official Android attestation roots, signatures, certificate status, extension provenance, expected challenge, key purpose/curve/origin, hardware security levels, locked verified boot, patch floors, app package and release certificate digest. Apply official Android path/expiration guidance (including root rotation and legacy attestation exceptions, not a generic accept-expired rule). Biometric key requires hardware-enforced per-use strong biometric, no password/device-credential fallback; test actual Keystore invalidation on biometric enrollment changes. Transport key is separate, hardware generated and not biometric-gated. No software fallback, debug APK or unverified attestation. App identity is attested at key creation, not continuously; attestation is not proof that every subsequent OS/UI state is uncompromised. Require periodic fresh re-enrollment/key replacement at most 30 days and upon policy/credential changes; revalidate stored chains against a revocation snapshot at most 24 h old before use. Unavailable or stale revocation/clock data blocks RBA, not local password. Patch floors and trust roots are explicit administrator configuration with no allow-all default. Host verifier must be maintained and independently reviewed; selection and platform feasibility are B.2 entry gates, not an excuse for a weaker production route.

References: [Android Key Attestation](https://developer.android.com/privacy-and-security/security-key-attestation), [Android attestation schema](https://source.android.com/docs/security/features/keystore/attestation), [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html). See normative wire details in PROTOCOL.md.

## 8. Design acceptance boundaries

No production implementation exists for this design. Exact Android native TLS/Keystore signing interface, attestation validator dependency, stable account lifecycle on target distro and trusted intent adapter must be demonstrated in isolated feasibility tests before implementation freeze. If not feasible, revise the complete design; never introduce a permissive production substitute. CI and physical acceptance are independent gates. Historical descriptions in README, architecture, pairing, versioning, SESSION_ADMISSION and AUTHORIZATION_MODEL remain V1 references until B.2/B.4 replaces them.
