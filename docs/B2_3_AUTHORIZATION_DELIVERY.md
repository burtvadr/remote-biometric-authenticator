## Host boundary

`linux/rbad/src/v2_store/authority.rs` owns the Store, live local requests, classified TLS peers, and one live pairing slot. Store security mutations are private to the storage module; external consumers use the authority. Existing storage-level prompt reservation is test-only; production-facing V2 dispatch uses a single immediate SQLite transaction with the same durable reservation helper. No alternate writable database or JSON fallback is added.

- `LocalIntent` is trusted internal adapter data, not IPC input. The CLI scope requires exact self target, authenticated UID and managed principal snapshot. A trusted service scope must be established by the actual configured service adapter, not a client claim. All caller, target and approver snapshots must match active account generations. The IPC/account-lifecycle adapter is not implemented by this unit; elevated scopes must not be enabled before actual provenance is validated.
- `begin` consumes a verified local-caller ingress budget even if grant lookup fails. It binds immutable credential, exact grant, current revision/digest and both deadlines. One live request per target, credential, interaction and local connection; 32 globally. Request IDs use OS randomness.
- `dispatch` accepts only the owning IPC connection and a classified peer with the exact active transport key. It rechecks the grant, current revision and digest, caller/target/approver identities and assurance freshness within the transaction that reserves prompt budgets and records the audit event. No grant or wrong peer means no prompt charge. No refund after successful reservation, including cancellation or disconnect. One dispatched request per TLS channel.
- `recheck_authorization` is a non-approval check, not an authentication result. B.2.4 must consume the exact response attempt, verify cryptographic evidence and local ownership, use the same `authorized` predicate in the final serialized success transaction, and deliver to the original live IPC requester without an intervening authorization gap. No success-returning biometric API is implemented here.
- `cancel_local`, `cancel_peer`, disconnect and policy changes invalidate only matching request ownership or the affected credential; account removal/enrollment replacement conservatively invalidate all live requests and classified peers. A denied connection remains in the resource accounting until the transport actually closes it. The adapter must observe `connection_denied`, terminate I/O and call `close` only after actual closure. Terminal commit/revocation receipts may be sent once on the original channel before closing; no further request is admitted.
- Pairing is one admitted slot globally with a 120-second absolute deadline, durable pairing budget, exact local owner and one connection attempt. Connection ownership is assigned on acceptance, not later at TLS classification, preventing a stale socket from attaching to a new pairing. PAKE, attestation, staging proof and local approval are mandatory before invoking enrollment commit. Those are B.2.4/B.3 responsibilities, not assumed verified by the admission unit. Revocation-only peers cannot enter biometric ingress/dispatch and only the exact bound key/token revocation operation can be admitted.

## Budgets

`admission.rs` centralizes the V2 limits. Resource counters are bounded, monotonic and process-local; potential prompts and pairing remain durable in SQLite. Pre-TLS global attempts 120/60s, per normalized source 12/60s, 32 live TCP sockets total, 4/source, at most 2 enrollment sockets. Source map <=1024; local caller map <=4096. Global connection attempts are charged even if later rejected by source/slot limits. Preclassification cumulative byte cap 256 KiB; absolute handshake deadline 5s; separate 5s maximum from completed handshake to classification. Adapter must call byte accounting before processing untrusted bytes and enforce absolute read/write/frame/idle deadlines and physical socket closure in B.3/B.4. TLS keys and exporter must be extracted from the actual handshake, not claimed by frames. BLE remains disabled until a verified ordered carrier exists; the BLE ingress policy is defined but not exercised by a real carrier.

Local ingress 30/60s; TCP enrolled ingress 30/60s; future BLE ingress 15/120s. No ingress event spends another principal's prompt budget. Durable global prompts 6/60s, target and credential 3/60s each; non-CLI elevated subset 1/60s each; global and eligible initiator pairing 5/300s. Rolling boundaries are half-open; durable reservations and audit commit together. Wall rollback is denied against both SQLite high-water and current-process observations; live expiry also uses monotonic time. Restart loses in-flight work and process-local resource counters, not committed potential-prompt/pairing reservations.

## Android policy intersection

`V2DevicePolicy.kt` is an immutable policy evaluator, using existing normative message schemas, canonical bytes and digest validation. It loads only a committed policy for an enrolled host/credential/approver, requires a positive host-compatible revision (1..Long.MAX_VALUE), exact grant intersection with the explicit local allow-list, and rejects stale or same-revision conflicting offers. No wildcard, empty-list default allow, inferred grant, or challenge-based policy installation. It does not advance policy itself; authenticated consent, receipt and durable activation belong to the B.2.4 Android state machine. The caller must verify host signature, channel, freshness and session before UI. A policy check is not biometric approval.
