# B.3.5 — Same-host PAKE offline cleanup and startup alias reclamation

## Implementation

- Host retains hashed random revocation tokens after the online retry window expires. The retry deadline is removed, not renewed. Unknown tokens abort the complete enrollment transaction; an already revoked matching record is idempotent. Only newly revoked credentials appear in the host replacement approval. No grants are inherited.
- Android accepts explicit locally selected, already-denied credential IDs and requires separate cleanup consent after native PAKE confirmation. The protocol verifies the old host ID AND public key and rejects duplicate IDs/tokens, the new credential itself and more than 32 old records before exposing any token. The owner stages exactly those records. New enrollment activation and old-record acknowledgment are one Android SQLite transaction, shared with status recovery. Loss of receipt or rollback leaves old records disabled, not acknowledged. The existing cleanup routine can finish them after receipt or on next exclusive startup; no deletion is inferred from a lost network response.
- Startup entry point opens the canonical store under the operation owner's mutex; validate the database, read and check every record's metadata, finish acknowledged revocations, then snapshot Keystore aliases and remove only exact V2 provisional names and role names absent from the complete inventory. Preserve other namespaces and all remaining recorded IDs. Missing/corrupt state or failed inventory stops cleanup. This API is not yet invoked by the concrete runtime; wiring the exclusive startup gate before any V2 network/UI work is mandatory at cutover. Current single-process manifest assumed; any future multi-process owner requires interprocess exclusion. Do not invoke this against test/alternate storage.

## Decisions and scope

Retain the random-token hashes alongside existing credential history indefinitely, independent of the 30-day online retry authorization. This makes expired-pin cleanup verifiable without allowing online use. Both development schemas change; explicitly initialize fresh disposable V2 test stores before enrollment, with no automatic reset/migration. A different host key/ID or missing host history cannot prove revocation; require explicit operator recovery, never delete based on such a failure. Expired or uncertain pending enrollment records are not automatically removed. Concrete UI, service routing, physical Android Keystore behavior and cutover remain open. No portable-core extraction or new dependencies; no SEC closure.

Independent SQLite: eight host and eight Android schema tests, including cleanup link constraints and rollback/reopen. These are not Android database/Keystore instrumentation. New Rust regression `offline_cleanup_after_retry_expiry_and_unknown_token_rollback` has not been compiled or executed here (Cargo unavailable). Run full host tests, `make vectors-kt`, both SQLite scripts, Android compilation and `:app:testDebugUnitTest --tests '*V2AliasReclamationTest'`. Physically verify interrupted key creation, old key loss, expired retry, same-host mismatch, lost commit receipt and restart after interrupted deletion; ensure pending and active aliases are preserved. Use an isolated test installation; never run sweeping deletion against production aliases with a test database.
