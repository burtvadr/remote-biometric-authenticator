# RBA V2 — Implementation and acceptance plan

**B.1 design delivery.** Base: `2b8e76d` archive plus B.0 patch. No executable changes. No code is production eligible until complete acceptance. This plan is a dependency order, not a sequence of temporary security remediations. Work in isolated V2 branch/state and test harness, not installed PAM. Review the [architecture](ARCHITECTURE_V2.md), [wire draft](../protocol/specification/PROTOCOL.md), [threat model](threat-model.md) and [26-finding register](security-audit.md) together.

## 0. B.2 entry gates (resolve before implementation freeze)

1. Verify B.0 Rust workspace, portable enrollment KAT, Kotlin, Android/JNI and actual CI on the exact local baseline. Record commit and toolchain. B.0 patch was applied to uploaded snapshot here, not verified against live main.
2. Demonstrate an Android TLS 1.3 backend with RFC 9266 exporter, real mutual TLS, and a hardware-backed unattended client key through Keystore signing without exporting it. Prefer shared Rust TLS engine with narrow JNI signing callback; check Android threading, provider behavior, certificate APIs and deadlines. No production prototype or unauthenticated fallback.
3. Select and review maintained Android attestation verifier and chain/status validation; validate official trust-anchor rotation and documented expiration rules. Demonstrate fresh per-key challenge, correct key policy and negative cases using test certificates and real release-signed phone. No handcrafted ASN.1 validation without independent review. Lock dependency versions and record licensing/advisories.
4. Establish real trusted local intent channel and provenance on supported Arch integrations, including whether the local PAM conversation can present the number. Test root-controlled account lifecycle/barrier. For unsupported adapters, leave scope disabled until a supported implementation exists; don't manufacture command context or use a bypass.
5. Review wire schemas, exact profile, PAKE application context and resource/clock bounds independently. Resolve policy and enrollment edge cases, generate independent canonical fixtures, then freeze profile. The B.1 target is detailed but not yet a reviewed interoperability standard. Changes to draft before freeze are not runtime migration.

## B.2 — Core

Create one portable Rust protocol and state-machine workspace; centralize lockfiles and feature gates. Extract codec/frame/signing logic from `linux/protocol`; replace `android/protocol` security implementation with shared native bindings. Keep JVM tests as adapter/fixture tests rather than duplicate authority. Retain the RFC library and known-answer tests in `crates/rba-enrollment`; change context/profile and JNI to the V2 design. Move authorization, admission and lifecycle from `linux/rbad` to `rba-core`, making I/O effects explicit; fake clocks/CSPRNG/store/transport only in test builds. Host SQLite store adapter owns one serialized transaction boundary. Define tables for host metadata, managed principals and generations, credentials and attestation metadata, grants/policy revisions, durable admission events, enrollment transactions, revocation tombstones and audit event outbox. Foreign keys and uniqueness on IDs/key binding; strict schema version, CHECK constraints, bounded records. Credential, initial grants, old-record revokes and enrollment receipt committed together. Revoke/change transactions invalidate pending requests. Audit outbox stores redacted outcomes; successful auth depends on durable security transaction, not log delivery. Define bounded tombstone retention 30 days; on expiry require explicit host admin cleanup. No automatic database recreation or state reader for old formats.

Tests: all map schemas, canonical negative fixtures, transcript oracle, RFC KAT, application context mutation, wrong keys/roles, expired/replayed evidence, resource quotas, independent counters, exact rolling boundaries, global limits, concurrent reservations, clock rollback, I/O failure, corrupt store, transaction ordering, stale cancellation, lost receipt and restart. Fuzz parsers and state transitions with reproducible corpus. Test results are evidence only for actual code revision. No claim of complete hardware trust from mocked verifier; test-only fake verifiers must be impossible in production build.

## B.3 — Trust, enrollment and Android

Replace `rbad/src/tls.rs` and Wi-Fi transport with one authenticated profile and temporary isolated enrollment listener. Build shared Android JNI transport/key/state bridge, with Kotlin only handling platform lifecycle, UI, Keystore and OS permission/biometric interfaces. Device must verify host challenge and matching receipt before signing exact response; test cancellation/background/recreation and malicious intent input. Fresh hardware keys, verified attestation and release identity required for every enrollment. Revocation data refresh and expiry policy mandatory. Real release package and signer pinned; signing secrets not committed or required by pull requests. Remove software fallback, old SAS/V1 paths, unverified TLS production verifier and production simulator trust. No BLE/ADB production transport until ordered-stream implementation can pass identical channel tests. TCP manual endpoint and supported explicit interface configuration first; discovery opt-in.

Acceptance: both code-entry directions on real phone; wrong code, wrong certificate/key/challenge, software/invalid boot/wrong signer/revoked/stale evidence, disconnect every stage, status recovery, offline unpair, replay and cross-channel failures. Actual release APK and native ABI builds, inspect APK/debug flag, verify signer and hardware evidence. Measure timing and resource usage, capture discovery privacy. Document specific physical model, OS/patch version and exact artifact hash. No production activation based on debug CI.

## B.4 — Host integration

Replace JSON IPC clients and server together. Specify the complete typed local ABI before coding those clients: `status`, `start-server`, `kill-server`, `devices`, `pair`, `unpair`, `grant`, `revoke`, `auth`, `inspect`, `policy`; each operation defines exact args/result, kernel-authenticated role, deadline and errors. Only trusted interaction adapters may stream `number-display`, `cancel`, and final result events on owning IPC connection. No number in argv or generic log. Status/list filtered by peer principal. Privileged daemon lifecycle through platform service manager; no accidental test daemon on production socket. Admin policy updates through authenticated exact scope and revision; ordinary self-pairing cannot expand grants. Never rely on executable name alone or generic root-string scope. Thin PAM client uses reviewed FFI, bounded transport, release unwind policy where catch_unwind is required; test panic across actual release FFI and avoid unsafe unwind. No daemon failure may imply PAM success. Only enable actual supported scopes after real local intent and service provenance verified. Keep original vendor password stack and local recovery; scoped `/etc/pam.d` override only after dry-run and root-shell recovery test. Do not install a competing desktop polkit agent as a workaround. GDM/polkit feature goals remain in roadmap if integration prerequisites not yet met. Update CLI docs, man pages, installer, configuration, architecture/versioning/pairing/authorization/admission docs to V2; remove old reader and runtime JSON dependencies. No legacy auth protocol process running as fallback.

## B.5 — Acceptance and release

Pin CI action commit SHAs, Rust/JDK/Gradle/NDK/SDK versions, dependencies and checksums; ensure lockfiles complete. CI required for format, Clippy, unit/integration/adversarial suites, independent vectors, JNI/Android unit/lint, release build verification without exposing secrets, parser and state-machine fuzz jobs. Record tool versions, commit, logs, test counts and build hashes. Physical validation and independent security review separate gates. Tests run against candidate release, not merely V1 fixtures. Full audit register maps each SEC to source, test, deployment evidence, responsible reviewer and disposition. No partial finding closure. Residual threat assumptions are stated; release blocked for unmet required security properties. No claims of formal proof or vulnerability-free system.

## Cutover and rollback

The B.3.5 V2-only source candidate is documented in `B3_5_RUNTIME_CANDIDATE.md`. It is not a deployed cutover and does not yet expose the verified B.4 local ABI.

Only after B.5: keep known-good independent OS password path, export non-secret operator configuration for review, stop old daemon, install V2 in fresh isolated state, verify service/key/socket permissions, enroll new release phone, test narrow CLI first and OS integrations one at a time. No V1 credential import or version fallback. Old files may be kept offline protected as evidence/recovery material, not read by V2. If any check fails, disable RBA and restore vendor password route; do not weaken trust policy. Never test first on the only usable login path. CLI output must truthfully state unsupported scopes and transport capability, no fake successful status.

## B.1 delivered evidence

Six coordinated Markdown documents only. Static comparison with uploaded snapshot and applied B.0 patch. No runtime implementation, fresh Rust/Kotlin fixtures, fuzzing, attestation or device tests performed. IPC operation-specific ABI, dependency choice and platform feasibility are explicit pre-implementation gates. Existing V1 code/docs outside the six files remain unchanged until the relevant phase; historical roadmap and audit retained to preserve evidence. A complete security remediation requires actual implementation and acceptance, not the existence of this plan.
