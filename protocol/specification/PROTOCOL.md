# Remote Biometric Authenticator — Protocol V2

**B.1 normative target draft, not the current executable protocol.** V1 source and fixtures remain at baseline `2b8e76d` + B.0; do not advertise V2 until both peers implement and pass this profile. This specification uses MUST/SHOULD as RFC 2119/8174 requirements. No downgrade, legacy format or permissive feature negotiation. Design acceptance and interoperability vectors are required before freezing V2. See [architecture](../../docs/ARCHITECTURE_V2.md) for policy and deployment prerequisites.

## 1. Primitives and encoding

TLS 1.3 (RFC 8446 and applicable updates), RFC 9266 `tls-exporter` (32 bytes), ECDSA P-256/SHA-256, SHA-256, RFC 9382 SPAKE2 P-256/SHA-256/HKDF/HMAC, OS CSPRNG. Use maintained libraries; no local curve arithmetic. Raw uncompressed SEC1 points (65 bytes, on-curve non-infinity); signature fixed-width 64-byte `r||s`, both scalars in 1..n-1. Both valid ECDSA S variants accepted; never use signature as identity or replay key. Convert Android DER strictly inside adapter, do not double-hash (Keystore SHA256withECDSA signs transcript bytes). Key identifiers = SHA-256(raw point); certificate fingerprints = SHA-256(exact DER). IDs random 16 bytes; challenges/nonces/tokens 32 bytes. All randomness OS CSPRNG. Unix seconds unsigned 64-bit, no leap-second special encoding; duration milliseconds unsigned. Display labels and context details use RBA Display Text 1: strict UTF-8, NFC, and only the exact scalar ranges in [the normative repertoire](../text-profile/rba-display-text-1.tsv). Reject rather than normalize signed input. The frozen repertoire uses UCD 15.0.0 categories L/M/N/P/S/Zs, Age <= 10.0, excluding Default_Ignorable_Code_Point; runtime category tables must not expand it. Android API 28 and later have Unicode >= 10.0; NFC stability for assigned characters permits maintained native normalizers. Reject private-use, noncharacters, unassigned/newer characters, format/control characters, and line/paragraph separators. This is not a defense against all visually confusable text: UI must separate trusted context fields and render labels as non-authoritative display data. IDs are not derived from addresses.

Deterministic CBOR per RFC 8949 §4.2.1: definite lengths, preferred shortest integer/length forms, bytewise lexicographic encoded key ordering. Only specified map keys, unsigned ints, bstr, tstr, arrays and maps; reject duplicates, unknown fields, tags, floats, indefinite items, negative ints, trailing bytes and noncanonical encoding. Bound nesting to 8 and total decoded items to 1024; reject before allocations beyond frame cap. Unless specified, text 1..128 UTF-8 bytes; arrays max 32; certificate DER list max 8 entries each 8192 bytes, combined payload subject to frame cap. Core provides one codec on both endpoints. Each schema below is exact; no implicit optional fields.

## 2. Channel and frame

TCP or a reliable ordered bounded full-duplex byte carrier -> TLS 1.3 -> RBA frame. No cleartext RBA, early data, resumption, ALPN fallback, or renegotiation. Separate ALPN `rba/2` (production) and `rba-enroll/2` (temporary listener). Host TLS server and Android client; enrollment permits provisional self-signed P-256 certs only in enrollment listener; both prove possession in TLS CertificateVerify. No trust decision solely from certificate presented during enrollment. Production uses exact enrolled key pins and host-configured validity/assurance checks; full client and server authentication mandatory. Transport key is distinct from biometric key. Android transport key authorizations require exactly SIGN, P-256, SHA-256 and NONE digest (the latter only for the selected Conscrypt opaque-key TLS prehash callback); biometric keys require SIGN, P-256, SHA-256 only and fresh strong biometric per operation. The TLS layer sends one leaf certificate, treated as a key carrier in production: exact registered pin, current assurance, certificate validity and TLS CertificateVerify are mandatory, not CA trust. Complete attestation chains are sent in enrollment EVIDENCE. Provisional client keys are fresh one-use local keys, never enrolled or reused. Exporter `B = TLS-Exporter("EXPORTER-Channel-Binding", empty context, 32)` obtained locally after full handshake; never use remotely supplied exporter or certificate digest. Transport changes invalidate B. Disable any backend unable to supply B and mutual authentication. BLE/ADB not enabled until reliable stream and TLS profile validated; same protocol on every supported carrier.

Frame 13-byte header: ASCII `PAF2` (4), version `0x02` (1), message type u16 BE (2), flags u16 BE = 0 (2), payload length u32 BE (4), then deterministic CBOR exact map. Payload 1..65536 bytes. Read fixed header and validate before body allocation. Consume exactly one frame, preserve next frame bytes; malformed/truncated/version/flags/unknown type closes channel without scanning magic or downgrade. No remote error detail for pre-auth failures. Limits: 32 simultaneous TCP connections globally, 4 per source; separate max 2 temporary enrollment connections, one live admitted pairing globally; 5 s total TLS handshake, 5 s frame completion, 30 s idle production; bounded queues (32 pending local requests globally, 1 live per credential/target); implementation must account for connections before TLS work. Before TLS, charge a global 120 connection attempts/60 s and per-source 12/60 s rolling budget, independently of active connection limits. Bound bytes to 256 KiB per connection before full enrollment/production peer classification, with handshake and frame caps thereafter; malformed input counts toward resource budgets, never toward another identity’s prompt budget. Source maps bounded to 1024 with expiration; global cap persists even if source map full (deny new source when full). Pairing window max 120 s. Deadline is absolute monotonic for operation, not refreshed by partial reads. Long human wait uses operation deadline and bounded keepalive/status outside frame-read timeout; idle 30 s applies only when no active enrollment/auth request. No unbounded packet or connection growth. No untrusted network bind by default: explicit operator-selected interface addresses, firewall guidance, separate temporary enrollment listener.

## 3. Shared types and signature construction

Notation `id16`, `b32`, `pk65`, `sig64`, `u`, `s`, `certs` as above. `scope = {purpose:s, service:s, operation:s}` where each identifier is ASCII `[a-z0-9._-]`, 1..64 bytes. Initial production operations: `authenticate/rba/authenticate`, `authenticate/sudo/service-auth`, `authenticate/gdm/session-auth`, `authenticate/polkit/action-auth`; only scopes backed by a verified integration and explicit grants may be enabled. The last three are not automatically authorized; service-auth is not exact command authorization. Future IDs are rejected unless supported by both peers; no generic privileged wildcard. `context = {source:s, detail:s, interaction_id:id16}`; source is a typed adapter ID, detail is bounded text (max 256 bytes, validated/sanitized before signing); no claim of trustworthy action beyond source's verified evidence. Phone uses immutable signed labels and locally enrolled host name. `capabilities` are sorted unique ASCII identifiers, <=32; mandatory core identifiers `number-match`, `attestation`, `tls-exporter`, `strong-biometric`; must all be present, capabilities never grant access. Unknown advertised nonrequired capabilities ignored, unknown requested scope rejected.

Signed object `S(domain, map) = ASCII(domain) || 0x00 || deterministic-CBOR(map)`; signature field is not in its own signed map. `H(domain,map) = SHA-256(S(domain,map))`. All domains exactly as listed (case sensitive). Host challenge signature uses `RBA-V2-AUTH-REQUEST`; host number-match acknowledgment uses `RBA-V2-MATCHED`; device evidence uses `RBA-V2-AUTH-RESPONSE`; enrollment proof uses `RBA-V2-ENROLL-KEY-PROOF`. Each endpoint compares canonical immutable fields with its local state. TLS exporter appears in signed maps and MUST equal the locally obtained B, not a transmitted assertion. No signature over human text alone.

## 4. Production session and authentication messages

Host sends HELLO first, client ACK. Both must check mandatory capabilities and match the TLS-authenticated peer to the stored binding before accepting any further message. Revoked transport pins may only enter the restricted revocation retry flow, and pending phone records may only enter enrollment-status recovery. Exact maps (`v` always u=2). No other message before hello except TLS itself. Every subsequent auth message carries the single `session_id` and `request_id` of this request. One auth request per channel; close after terminal outcome. Administrative policy sync and revocation use separate channels with same hello binding, never interleave auth. An idle pre-auth channel may not trigger a prompt. HELLO_ACK MUST specify immutable connection purpose: 0 authentication wait, 1 policy synchronization, 2 enrollment-status recovery, 3 revocation. The receiver rejects any other purpose or message outside that class. A revocation-only pin may select only 3. This field is protected by TLS and selects routing only; it never creates a local operation or grants authority. No compatibility with HELLO_ACK lacking purpose.

Terminal success receipts (`AUTH_RESULT` with outcome 1, `REVOKE_RECEIPT`, `ENROLL_RECEIPT`, committed `ENROLL_STATUS_RESULT`) MUST be the exact authority-produced frame after the relevant operation is verified and durably committed or the committed record has been verified. Consume the operation and revoke ordinary I/O first; the owning TLS channel may write that one frame only, then close. No generic exception for denied connections, retry on the same channel, caller-supplied replacement receipt, additional application reads, or renewal of the operation deadline. Limit terminal delivery to five seconds and never beyond the original auth/enrollment deadline; use both wall and monotonic clocks. Socket loss, expiry, relevant revocation or trust invalidation may prevent delivery without undoing a committed operation. Enrollment status recovery and idempotent revocation retry use a fresh authenticated channel. A terminal receipt is not an OS authentication token. A failed or cancelled operation can close without a receipt; no success receipt is generated on failure. Policy-sync lifecycle requires its own complete verified transitions.

`AuthCore` exact map: `{v, session_id:id16, request_id:id16, host_id:id16, credential_id:id16, host_nonce:b32, device_nonce:b32, channel:b32, challenge:b32, approver:id16, target:id16, approver_label:s, target_label:s, scope:scope, context:context, policy_revision:u, issued_at:u, expires_at:u}`. The host signs AuthCore. Device verifies host pin/signature, both nonces, channel, IDs, expiry, exact active grant and policy revision, and local constraints before presenting UI. If policy is missing or out of sync, deny and require a separate policy sync; no implicit acceptance from a signed challenge. No number or digest of number in AuthCore. Host retains number only in volatile owned request and displays it via verified local interaction; 6 uniformly sampled digits, leading zeros. The phone accepts manual input only (no autofill, clipboard or number in initial challenge). Host compares single entry in constant time and clears number; failure is terminal. Correct input is not authentication; host sends signed MatchCore.

`MatchCore = {v, session_id:id16, request_id:id16, channel:b32, request_hash:b32, matched:u}`; matched=1; request_hash=H("RBA-V2-AUTH-REQUEST",AuthCore). Device verifies match before starting per-use strong biometric CryptoObject signature. `ResponseCore = {v, session_id:id16, request_id:id16, channel:b32, request_hash:b32, match_hash:b32, credential_id:id16, decision:u}`; decision=1 only, match_hash=H("RBA-V2-MATCHED",MatchCore). Device signs ResponseCore with enrolled biometric key, never transport key. No bare approval, arbitrary signing callback or authentication on UI result alone. Host verifies against immutable pending state and current attested key, consumes attempt before checking evidence, rechecks current grant/revision/assurance, expiry and caller ownership in one serialized transaction before returning success to original IPC owner. Device rejection uses CANCEL. Cancel or result cannot affect a different request. Duplicate, late, mismatched or out-of-order messages close channel and cannot authorize.

Freshness: host sets `expires_at = issued_at + 60` seconds, or a shorter whole-second duration from adapter policy (1..60). Host enforces monotonic deadline and wall deadline; device requires `issued_at <= now + 5`, `now < expires_at`, `1 <= expires_at-issued_at <=60`; no grace after expiry. Device also starts a monotonic deadline capped at remaining wall duration. Clock rollback, invalid trusted clock or arithmetic overflow denies. Host checks expiry again at commit. No persistent in-flight requests, no retry of same challenge; random IDs and fresh exporter prevent replay after restart. Failover creates entirely new request and number, never extends old deadline. Disconnection invalidates pending request and all UI handles.

`GrantView = {credential_id:id16, approver:id16, target:id16, scope:scope}`. Grant arrays sorted by canonical encoded bytes and unique; digest H("RBA-V2-POLICY", {revision,grants}). Policy revision is per credential, strictly increasing and durably stored; phone rejects older or same-revision conflicting digests. Host only originates POLICY_OFFER; device constraints are local and intersect with host grants; device may decline any offered policy and never propose broader rights via this message. Host uses one outstanding offer per credential, monotonically increasing revision and exact digest, with explicit device consent for expansion. Commit after accepted decision on same channel, send receipt; removal immediate and cannot be blocked by phone; missing receipt leaves device on narrower policy and requires a fresh offer. Any revision change invalidates live authentication; synchronization cannot grant rights absent host authority. Full capability UI and device-side policy management remain later roadmap features, but core intersection is mandatory.

## 5. Enrollment-only channel

Explicit local authorized action creates one enrollment ID `e`, a random host attestation nonce, and a 120 s deadline; one connection/attempt only, with exactly one CSPRNG six-digit code. Entry direction `0` device types host code, `1` host types phone code; displaying endpoint generates code. Host always RFC 9382 A, phone B. Actual provisional TLS peer keys/fingerprints are known before PAKE. The fresh long-term device transport key MUST be generated for this host challenge. To avoid circular TLS identity/attestation, initial provisional client TLS key is ephemeral and distinct; after PAKE the fresh long-term transport key is proven and attested and used on subsequent production connection. The provisional key is never a registry credential. Host attestation nonce is sent in START and bound to B. Both endpoints display observed host and device key fingerprints (full SHA-256 accessible) and source as routing information only; explicit consent after PAKE verification. No code in argv, wire or logs; entry is protected stdin/local UI. No automatic enrollment on discovery. Existing credential replacement requires explicit host authorization and valid old revocation token or explicit old-record revocation; never inherit grants implicitly.

START expiry max 120 s from host creation; same strict expiry/no extension as auth, with 120 s cap and monotonic deadline. Device generates new hardware-backed keys after START, before share. Attestation challenge for each key = H("RBA-V2-ATTEST", {v,enrollment_id,host_id,nonce,channel:B,role:u}); role 0 transport, 1 biometric. Actual leaf public key must equal corresponding SHARE key. Attestation chains and proofs sent only after mutual PAKE confirmation. Key proof map `{v,enrollment_id,host_id,credential_id,channel:B,nonce,transport_key,biometric_key,role:u}` signed by respective key; biometric proof requires explicit fresh strong biometric (enrollment consent, distinct from OS authentication). Host validates both chains and proofs, local explicit approval, account and initial scope before OFFER. No grants or tokens before confirmation and evidence validation. Device may send only tokens for same enrolled host after confirmation. Host atomically revokes exactly token-matched previous records and commits new record only after staged acknowledgement. Offer_hash=H("RBA-V2-ENROLL-OFFER", exact OFFER map); receipt and token are independent random b32. Store receipt hash and offer hash, transaction ID and committed status. Status recovery: a newly enrolled transport key may connect via production mTLS and HELLO, then send ENROLL_STATUS with exact transaction ID and receipt. Host compares stored hash and returns same receipt if committed and active, otherwise generic reject or absent only to authenticated matching credential. Status never creates or expands trust. Phone verifies returned receipt equals staged value; persists activation before reporting complete. Host success only after commit. Pending state cannot approve auth. Receipt recovery does not extend the key assurance lifetime or resurrect revoked credentials. Commit and cancellation ordering as architecture. Uncommitted phone state is removed on explicit abort or verified rejection; uncertain loss retains a bounded pending record for status or explicit re-enrollment. No indefinite live pairing session.

### 5.1 SPAKE2 profile

Reuse vetted RFC 9382 library primitive, not a new PAKE. Password scalar profile from baseline: SHA-512(ASCII `RBA-ENROLLMENT-SPAKE2-PASSWORD-V2` || NUL || six ASCII digits), reduced mod P-256 group order by library; reject zero if library requires; single-use random code only. Confirmations use RFC 9382 suite as implemented by reviewed library. A identity host_id, B identity credential_id. Replace old 219-byte AAD with `S("RBA-V2-ENROLL-CONTEXT", {v,enrollment_id,host_id,credential_id,nonce,expires_at,direction,suite,channel:B,host_cert:b32,provisional_client_cert:b32,host_key:pk65,provisional_client_key:pk65,transport_key:pk65,biometric_key:pk65})`, certificates and keys from actual handshake, not claimed hashes. Both long-term device keys as in SHARE. Device computes B share after local code and context; host computes A share after local code and SHARE. Device verifies A confirmation before B; host verifies B before EVIDENCE. All post-confirmation messages travel on same exact TLS channel whose exporter and certs were confirmed. No raw PAKE key exported to Kotlin; no second application encryption/MAC scheme. Drop secret state on failure, timeout, cancel or success. RFC KAT and profile review required, including password-scalar interoperability and transcript binding. No legacy SAS fallback.

## 6. Revocation, persistence and local IPC

REVOKE only over enrolled mTLS for that exact credential and token hash; no auth grant from token. Commit revocation before receipt; close all sessions and deny new auth immediately. Retry idempotently while a bounded revocation-only tombstone pin remains; that pin may connect only to revoke, never authenticate. Offline cleanup uses a new enrollment after confirmed same-host PAKE, matching both the stored host ID and host public key. Only explicitly selected, durably locally denied credentials may supply cleanup tokens. The host MUST reject unknown token hashes, treat previously revoked matches idempotently, and retain token hashes when the online retry pin expires; this does not renew retry authority. Android MUST stage the exact cleanup set atomically with the new pending record, acknowledge the old revocations only on verified commit receipt or exact status recovery, and delete old keys only after durable acknowledgment. Startup key reclamation requires exclusive ownership, a validated canonical database and a complete inventory; preserve all recorded credentials (including pending, expired and locally denied) unless cleanup is durably acknowledged. Host admin revoke always available. No secret logging. No automatic activation on state corruption or restart.

Local control protocol: Unix peer-authenticated socket, fixed u32 BE length 1..65536 and canonical CBOR `{v:2, id:id16, op:s, args:map}`; response `{v:2,id:id16,status:u,result:map}`. Version/size/operation-specific exact schema required; one request per connection except explicitly typed local interaction events. Local operation registry is part of B.4 implementation contract (see IMPLEMENTATION_V2); this is not a complete local IPC ABI. Security-sensitive context derived from verified adapter, never arbitrary args. Bounded read/write/connect deadlines and peer verification both ways; no production socket override. No export of portable approval tokens. Recovery outside RBA independent password route.

## 7. Discovery, diagnostics and conformance

Manual/configured endpoint default; opt-in discovery generic service label and ephemeral routing hints only, no host/key/device/account IDs or stable names in mDNS/BLE advertisements. TLS authenticates endpoints after routing. No unsolicited pairing mode. Logs include bounded event type, local opaque IDs, outcome class and time; exclude codes, tokens, biometric data, full certs, signatures, exporter, raw details and private keys. Account/host presence never exposed to unauthenticated remote peers; local authorized users may observe their own availability. Timing measurements under defined threat model required, no absolute constant-time network claim.

Tests: deterministic encode/decode fixtures for every message; signed transcript and exporter mutation; RFC 9382 KAT plus application-context known-answer vectors; independent fixture oracle for signed maps (not merely one implementation testing itself); version rejection, malformed lengths/maps/keys, invalid state transitions, replay/cross-channel substitution, expiry boundaries, budget concurrency and persistence faults, enrollment crash/receipt recovery, policy revision races and fuzz targets for frame, CBOR, attestation, IPC and JNI. Simulator isolated from production trust. No V2 runtime release until physical release APK, actual TLS/Keystore exporter and attestation verification, local recovery and full audit gates pass.
